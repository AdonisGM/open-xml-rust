0.2 Cài Rust & bộ công cụ cargo

Bài này biến máy của bạn thành "xưởng" để làm việc với open-xml-rust: cài Rust, hiểu ba công cụ rustup – rustc – cargo, chạy bộ test lần đầu, đọc từng dòng kịch bản kiểm tra chất lượng của dự án, và cuối cùng dùng chính công cụ dòng lệnh của dự án để "mổ" file .docx — lần này bằng Rust.

⏱ ~45 phút (chưa tính thời gian build lần đầu)File: Cargo.toml, rustfmt.toml, scripts/check.sh, .gitignoreCrate: openxml-xml, openxml-cli

🎯 Học xong bài này bạn sẽ

  • Phân biệt được rustup, rustc, cargo và biết mỗi thứ nằm ở đâu trên máy.
  • Hiểu toolchain, edition và rust-version — ba khái niệm "phiên bản" hay bị nhầm lẫn — qua đúng Cargo.toml của dự án.
  • Dùng thạo các lệnh cargo check / build / run / test / doc / fmt / clippy cùng các cờ -p, --workspace, --release, --example và dấu --.
  • Đọc được output của cargo test: unit test, integration test, doc-test.
  • Hiểu target/, Cargo.lock, debug vs release, và vì sao dự án bật opt-level = 1 cho các dependency.
  • Đọc hiểu từng dòng scripts/check.sh — "cổng chất lượng" mà mọi thay đổi phải đi qua.
  • Chạy openxml info trên một file thật và nhận ra package, part, content type, relationship từ bài 0.1.

1. Ba cái tên: rustup, rustc, cargo

Người mới hay bối rối vì cài "Rust" xong thì có tới ba lệnh. Hãy hình dung một xưởng mộc:

rustc
Trình biên dịch (compiler) — "cái máy cưa". Nhận file .rs, sinh ra file thực thi hoặc thư viện. Bạn gần như không bao giờ gọi trực tiếp nó trong một dự án thật.
cargo
Trình quản lý dự án và build — "người quản đốc". Đọc Cargo.toml, tải thư viện ngoài (dependency) từ crates.io, gọi rustc đúng thứ tự cho từng crate, chạy test, sinh tài liệu… Đây là lệnh bạn gõ cả ngày.
rustup
Trình quản lý phiên bản (toolchain manager) — "người mua máy móc". Cài, cập nhật, chuyển đổi giữa các bộ rustc + cargo + công cụ phụ (rustfmt, clippy, rust-analyzer…).

1.1 Cài đặt

  1. macOS / Linux: chạy lệnh cài chính thức từ rustup.rs, chọn mặc định (option 1). Xong thì mở terminal mới (hoặc source "$HOME/.cargo/env").
  2. Windows: tải rustup-init.exe từ rustup.rs. Trình cài sẽ nhắc cài "Visual Studio C++ Build Tools" (cần cho bước link) — cứ làm theo.
  3. Kiểm tra: rustc --version, cargo --version, rustup show.
  4. (Tuỳ chọn) xmllint: một số test kiểm tra XML sinh ra bằng XSD qua xmllint. macOS có sẵn; Ubuntu/Debian: sudo apt install libxml2-utils. Không có thì các test đó tự bỏ qua (xem mục 7).

🦀 Góc Rust — kênh phát hành (channel)

Rust ra bản mới 6 tuần một lần trên kênh stable. Ngoài ra có beta (bản sắp ra) và nightly (mỗi đêm, có tính năng thử nghiệm). Dự án này chỉ cần stable. Lệnh rustup update kéo bản stable mới nhất. Rust giữ cam kết tương thích ngược: code viết cho 1.88 vẫn build được trên 1.94 — chỉ có thể xuất hiện thêm cảnh báo mới (mục 9 bạn sẽ thấy đúng một ví dụ như vậy).

2. Toolchain, edition, rust-version: ba chữ "phiên bản"

Mở Cargo.toml ở gốc repo. Phần mình quan tâm bây giờ là khối [workspace.package] — các thông tin mà cả 12 crate dùng chung (bài 1.1 sẽ mổ xẻ phần còn lại của file này):

  • version = "0.1.0" — phiên bản của dự án (theo SemVer). Không liên quan tới Rust.
  • edition = "2024" — phiên bản ngôn ngữ mà code được viết theo.
  • rust-version = "1.88" — phiên bản trình biên dịch tối thiểu (MSRV — Minimum Supported Rust Version).

2.1 Edition là gì?

Vấn đề: ngôn ngữ nào cũng muốn sửa những quyết định cũ chưa hay (thêm từ khoá mới, đổi quy tắc), nhưng sửa thì code cũ vỡ. Rust giải quyết bằng edition: cứ vài năm có một edition (2015, 2018, 2021, 2024). Mỗi crate tự chọn edition của mình trong Cargo.toml. Cùng một rustc biết biên dịch mọi edition, và crate edition 2021 vẫn gọi được crate edition 2024 bình thường.

Ví dụ đời thường: edition giống "phiên bản quy chuẩn chính tả" của một tờ báo. Bài cũ vẫn in theo quy chuẩn cũ, bài mới theo quy chuẩn mới, cùng một nhà in in được cả hai.

Edition 2024 cần rustc ≥ 1.85. Nó thay đổi vài quy tắc tinh tế (phạm vi sống của biến tạm trong if let, từ khoá dành riêng gen…) mà bạn chưa cần để ý lúc này.

2.2 Vì sao lại là 1.88?

rust-version nói với cargo: "đừng cố build dự án này bằng rustc cũ hơn 1.88". Nếu ai đó dùng rustc 1.86, cargo dừng ngay với một thông báo rõ ràng thay vì một đống lỗi cú pháp khó hiểu. Con số 1.88 không ngẫu nhiên: đó là bản ổn định hoá let chains (chuỗi if let … && let …) — và chỉ cho edition 2024. Dự án dùng nó hơn 50 chỗ, ví dụ:

Đừng lo về &, Option hay pub(crate) — bạn sẽ học dần. Chỉ cần nhìn dòng 75–76: "nếu c là một nhóm hình GrpSp(g) và tìm đệ quy trong g ra kết quả". Trước 1.88 phải viết hai if let lồng nhau. Đây là lý do cụ thể khiến MSRV là 1.88: dùng một tính năng ngôn ngữ thì phải khai báo đúng phiên bản tối thiểu có tính năng đó.

⚠️ Chỗ hay nhầm

Toolchain (rustc 1.94.1 trên máy bạn) ≠ edition (2024, quy tắc ngôn ngữ) ≠ rust-version (1.88, mức tối thiểu). Bạn hoàn toàn có thể — và nên — dùng toolchain mới hơn rust-version. Dự án không có file rust-toolchain.toml, nghĩa là nó không ghim một toolchain cụ thể: ai dùng stable mới nhất cũng được.

Một dòng liên quan ở đầu file: resolver = "3". Đây là thuật toán cargo dùng để chọn phiên bản dependency; bản 3 "biết" rust-version nên ưu tiên chọn những bản dependency vẫn build được với Rust 1.88. Bài 1.1 sẽ nói thêm.

3. Lần build đầu tiên: chuyện gì xảy ra?

Gõ cargo build ở gốc repo. Lần đầu tiên sẽ khá lâu, và bạn sẽ thấy hàng loạt dòng Compiling …. Trình tự:

  1. Cargo đọc Cargo.toml gốc → biết workspace có 12 crate.
  2. Đọc Cargo.lock → biết chính xác phiên bản của từng dependency ngoài (quick-xml 0.42.0, zip 8.6.0…), tải về ~/.cargo/registry nếu chưa có.
  3. Dựng đồ thị phụ thuộc và biên dịch từ "lá" lên: memchr → quick-xml → openxml-xml → openxml-opc → … Các crate không phụ thuộc nhau được biên dịch song song.
  4. Kết quả đặt trong target/debug/.

Khi mình chạy cargo run -p openxml-cli lần đầu (các crate tầng dưới đã build sẵn), riêng đoạn biên dịch openxml-schema trở lên mất khoảng 1 phút 10 giây. Thủ phạm là 215 nghìn dòng code sinh tự động trong openxml-schema (bài 0.3). Những lần sau cargo chỉ biên dịch lại crate có thay đổi — nhanh hơn nhiều.

💡 Mẹo

Khi đang học một tầng thấp, hãy luôn thêm -p <crate>. cargo test -p openxml-xml chỉ cần biên dịch openxml-xml + quick-xml + memchr — vài giây là xong, thay vì chờ cả workspace.

Và các cờ bạn sẽ gõ nhiều nhất:

-p <crate>
(--package) chỉ làm việc với một crate: cargo test -p openxml-opc. Tên dùng ở đây là tên trong [package] name, có gạch ngang.
--workspace
áp dụng cho tất cả crate trong workspace. Ở gốc workspace, cargo test không kèm -p vốn đã chạy mọi thành viên, nhưng viết rõ --workspace (như scripts/check.sh) thì không phụ thuộc bạn đang đứng ở thư mục nào.
--release
build với tối ưu hoá đầy đủ (mục 6). Kết quả vào target/release/.
--example <tên>
chạy một file trong thư mục examples/ của crate: cargo run -p openxml-docx --example create_report -- out/report.docx.
--
"hết tham số của cargo". Mọi thứ phía sau được chuyển cho chương trình được chạy. cargo run -p openxml-cli -- info a.docx: info a.docx là tham số của CLI. cargo test -- --nocapture: --nocapture là tham số của bộ chạy test.
-q
(--quiet) bớt dòng Compiling….
⚠️ Chỗ hay nhầm — gạch ngang và gạch dưới

Tên package là openxml-xml (gạch ngang) — dùng trong Cargo.toml và -p. Nhưng trong code Rust, tên crate bị đổi thành openxml_xml (gạch dưới) vì - không hợp lệ trong định danh: use openxml_xml::Ns;. Thư mục tài liệu cũng là target/doc/openxml_xml/.

5. Chạy test lần đầu: cargo test -p openxml-xml

Crate thấp nhất, nhỏ nhất, chạy nhanh nhất. Đây là output thật trên máy mình (đã lược bớt phần giữa):

5.1 Đọc output từng khối

  1. warning: … — cảnh báo của trình biên dịch, không làm test thất bại. Cảnh báo này nằm trong code test của validate.rs: tạo một Box (cấp phát trên heap) chỉ để gọi một method là thừa. Mục 9 sẽ cho thấy vì sao nó quan trọng với check.sh.
  2. Finished `test` profile [unoptimized + debuginfo] — build ở profile test (kế thừa từ dev): không tối ưu, có thông tin debug. 0.02s vì mình đã build trước đó.
  3. Running unittests src/lib.rs (target/debug/deps/openxml_xml-4e14…) — cargo biên dịch mỗi "test target" thành một file thực thi riêng rồi chạy nó. Đuôi hash giúp phân biệt các bản build khác cấu hình.
  4. test ns::tests::strict_maps_to_transitional ... ok — tên test là đường dẫn module: file ns.rs → module ns → module con tests → hàm strict_maps_to_transitional. Thứ tự in ra có thể khác nhau mỗi lần vì test chạy song song trên nhiều luồng.
  5. test result: ok. 63 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out — tổng kết. ignored là test đánh dấu #[ignore]; filtered out là test bị lọc bỏ vì bạn truyền tên cần chạy.
  6. Doc-tests openxml_xml — các đoạn code nằm trong chú thích tài liệu (///, //!) cũng được biên dịch và chạy như test. openxml-xml không có ví dụ nào trong doc nên là 0.

5.2 Unit test nằm ở đâu?

openxml-xml không có thư mục tests/. 63 test kia nằm ngay trong các file nguồn, trong một module đặc biệt ở cuối file:

  • #[cfg(test)] — một attribute (thuộc tính gắn lên code): "chỉ biên dịch module này khi đang build để test". Bản build thường không chứa code test.
  • mod tests { … } — một module con tên tests (tên chỉ là quy ước).
  • use super::*; — kéo mọi thứ của module cha (ns) vào, kể cả thứ private. Đây là lợi thế của unit test nằm cùng file: test được cả hàm nội bộ.
  • #[test] — đánh dấu hàm là một test. Test thành công nếu hàm chạy hết; thất bại nếu nó panic (ví dụ assert_eq! thấy hai giá trị khác nhau, hoặc unwrap() gặp None).
📦 Góc OpenXML — test này kiểm tra điều gì?

Nhớ bài 0.1: file Strict dùng namespace URI khác (http://purl.oclc.org/ooxml/wordprocessingml/main) với file Transitional (http://schemas.openxmlformats.org/wordprocessingml/2006/main). Test khẳng định: đọc URI Strict ra đúng hằng Ns::W, và khi hỏi lại URI thì nhận được bản Transitional. Đó chính là cơ chế "đọc Strict, ghi Transitional" được mô tả trong ARCHITECTURE.md. Tên test thường là một câu mô tả hành vi — đọc danh sách tên test là cách nhanh để biết crate làm gì.

6. target/, .gitignore và Cargo.lock

6.1 Thư mục target/

Mọi thứ cargo sinh ra nằm trong target/ ở gốc workspace (một thư mục chung cho cả 12 crate — nhờ vậy dependency chỉ biên dịch một lần):

Thư mục này rất to — trên máy mình lúc viết bài là khoảng 2 GB. Xoá thoải mái bằng cargo clean; cái giá là lần build sau phải biên dịch lại từ đầu.

6.2 .gitignore

  • /target — không bao giờ commit sản phẩm build. Dấu / đầu nghĩa là "chỉ thư mục target ở gốc repo".
  • /docs/*.pdf, /docs/*.zip — bản PDF của chuẩn ECMA-376 (hơn 5.000 trang) và các gói zip gốc chỉ giữ trên máy tác giả; phần "máy đọc được" (XSD, JSON) thì được đưa vào schemas/. Ta sẽ nói về schemas/ ở mục 11 và bài 0.3.
  • /out — nơi các example ghi file ra (cargo run -p openxml-docx --example create_report -- out/report.docx). Bạn cứ ghi vào đó, git sẽ lờ đi.

6.3 Cargo.lock

Cargo.toml nói khoảng phiên bản chấp nhận được: quick-xml = "0.42" nghĩa là "bất kỳ 0.42.x nào". Cargo.lock ghi chính xác bản đã chọn kèm checksum:

File này có 34 mục [[package]]: 12 crate của workspace + 22 crate bên ngoài (quick-xml, zip, flate2, roxmltree, serde…). Dự án commit Cargo.lock vào git, nên ai clone về cũng build với đúng cùng một bộ dependency — "chạy được trên máy tôi" thành "chạy được trên mọi máy". Không sửa tay; muốn nâng cấp thì cargo update.

7. Debug vs release, và opt-level = 1 cho dependency

Dùng khiViết code, chạy testĐo hiệu năng, chạy corpus lớn, phát hành

Dự án có một tinh chỉnh nhỏ nhưng khôn ngoan ở cuối Cargo.toml:

  • [profile.dev…] — chỉnh profile dev (cũng là profile mà test kế thừa).
  • .package."*" — áp dụng cho mọi package không phải thành viên workspace, tức là các dependency ngoài: quick-xml, zip, flate2, zlib-rs, memchr…
  • opt-level = 1 — tối ưu nhẹ cho chúng.

Vì sao? Test của dự án làm việc nặng: round-trip mọi part XML của mọi file trong fixtures/, thử 2.000 đột biến ngẫu nhiên có kiểm soát (theo bảng test trong ARCHITECTURE.md)… Phần lớn thời gian chạy nằm ở giải nén ZIP và phân tích XML — đều là code của dependency. Tối ưu chúng làm test nhanh hẳn. Cái giá gần như bằng không: dependency hiếm khi thay đổi nên chỉ biên dịch một lần rồi nằm trong cache. Còn code của chính dự án — thứ bạn sửa liên tục — vẫn ở opt-level 0 để biên dịch lại nhanh và dễ debug.

🧩 Kỹ thuật — tối ưu có chọn lọc

"Tối ưu phần ít thay đổi, giữ nhanh phần hay thay đổi" là một mẹo phổ biến trong các dự án Rust lớn (game engine như Bevy cũng khuyên làm y hệt). Cách khác: chạy test với --release — nhưng khi đó mọi lần sửa một dòng đều phải biên dịch tối ưu lại cả crate của bạn, rất chậm với 215 nghìn dòng code sinh.

Còn unsafe_code = "forbid": cấm tuyệt đối từ khoá unsafe trong toàn dự án. Mỗi crate "đăng ký" luật này bằng hai dòng [lints] / workspace = true trong Cargo.toml của nó. Nghĩa là mọi đảm bảo an toàn bộ nhớ của Rust được giữ nguyên vẹn — một cam kết chất lượng khác, cùng tinh thần với mục 9.

8. rustfmt.toml và cargo fmt

Cả file chỉ có một dòng: cho phép mỗi dòng code dài tối đa 110 ký tự (mặc định của rustfmt là 100). Mọi thứ khác theo phong cách chuẩn của Rust. Lợi ích của việc có một formatter "không thương lượng": không ai tranh cãi chuyện xuống dòng, diff trên git chỉ chứa thay đổi thật.

Chi tiết thú vị: trình sinh code cũng dùng file này.

  • Dòng 54: env!("CARGO_MANIFEST_DIR") là thư mục chứa Cargo.toml của crate openxml-codegen (cargo cung cấp lúc biên dịch). ../../rustfmt.toml đi ngược hai cấp về gốc repo.
  • Dòng 55–68: chạy chương trình rustfmt như một tiến trình con, bơm code qua stdin, đọc code đã định dạng từ stdout.

Hệ quả: nếu ai đó đổi max_width, toàn bộ 215 nghìn dòng code sinh sẽ được định dạng khác đi và bước kiểm tra "code sinh còn mới không" (mục 9) sẽ báo lỗi cho tới khi chạy lại generator. Một file cấu hình một dòng, nhưng ảnh hưởng cả dự án.

9. scripts/check.sh — quy trình chất lượng của dự án

README ghi: "scripts/check.sh — fmt, clippy, generated-code freshness, all tests". Đây là một lệnh duy nhất gom mọi kiểm tra mà dự án dựa vào. Trước khi coi một thay đổi là "xong", chạy nó. Cả file:

9.1 Hai dòng "dàn trận" (7–8)

set -euo pipefail là ba công tắc an toàn của bash, gần như mọi script nghiêm túc đều có:

-e
Lệnh nào thất bại (mã thoát khác 0) thì dừng cả script ngay. Không có nó, cargo fmt báo lỗi xong script vẫn chạy tiếp và cuối cùng in "all checks passed" — tai hại.
-u
Dùng biến chưa gán giá trị là lỗi (thay vì âm thầm coi là chuỗi rỗng). Chính vì cờ này mà dòng 20 và 22 phải viết ${OPENXML_REQUIRE_XMLLINT:-0} và ${OPENXML_CORPUS:-}: cú pháp :- nghĩa là "nếu biến chưa có thì dùng giá trị mặc định sau dấu :-" (0, hoặc chuỗi rỗng).
-o pipefail
Trong một chuỗi a | b, nếu a hỏng thì cả chuỗi tính là hỏng (mặc định bash chỉ nhìn lệnh cuối).

cd "$(dirname "$0")/..": $0 là đường dẫn tới chính script, dirname lấy thư mục chứa nó (scripts), /.. đi lên một cấp — gốc repo. Nhờ vậy bạn gọi scripts/check.sh từ đâu cũng được.

9.2 Bước 1 — định dạng (dòng 11)

cargo fmt --all -- --check: --all là mọi crate; sau -- là tham số cho rustfmt: --check nghĩa là không sửa file, chỉ in phần khác biệt và trả mã lỗi nếu có. Muốn sửa thật thì chạy cargo fmt --all (không --check).

9.3 Bước 2 — lint (dòng 14)

cargo clippy --workspace --all-targets -- -D warnings:

  • --all-targets: kiểm tra cả thư viện, binary, test, example và bench — không chỉ code chính.
  • -D warnings: deny — biến mọi cảnh báo thành lỗi. Dự án giữ nguyên tắc "không một warning nào".
⚠️ Chuyện có thật khi mình viết bài này

Lúc mình viết bài, với rustc/clippy 1.94.1, lệnh cargo clippy -p openxml-xml --all-targets -- -D warnings thất bại vì lint unused_allocation ở crates/openxml-xml/src/validate.rs. Dòng bị báo nằm trong code test, nên chỉ lộ ra khi có --all-targets:

error: unnecessary allocation, use `&` instead
   --> crates/openxml-xml/src/validate.rs:202:9
    = note: `-D unused-allocation` implied by `-D warnings`

Nhiều khả năng toolchain lúc tác giả viết code chưa báo trường hợp này. Bài học: -D warnings + toolchain không ghim cứng = bản Rust mới có thể "làm đỏ" CI dù không ai sửa code. Các dự án xử lý bằng cách ghim toolchain (rust-toolchain.toml) hoặc sửa ngay khi lint mới xuất hiện.

Repo đã chọn cách thứ hai. Dòng bị báo là Box::new(p).validate(&mut v);. Chỗ tinh tế: test này cố ý gọi qua Box để kiểm tra phần impl Validate for Box<T>, nên nếu chỉ sửa thành p.validate(&mut v) thì hết cảnh báo nhưng test lại không còn kiểm tra điều nó muốn. Cách sửa giữ được mục đích là tách ra một biến: let boxed = Box::new(p); boxed.validate(&mut v);. Bài học: khi sửa một cảnh báo, hãy hỏi "dòng này đang muốn làm gì" trước khi làm theo gợi ý của công cụ. Giờ scripts/check.sh chạy qua toàn bộ.

9.4 Bước 3 — code sinh còn "tươi" không (dòng 17)

cargo run -q -p openxml-codegen -- --check chạy trình sinh code ở chế độ kiểm tra. Bên trong nó:

Ý tưởng: sinh lại toàn bộ code trong bộ nhớ từ các file XSD, so với file đang commit trong crates/openxml-schema/src/generated/. Khác một byte → file đó "cũ" (stale) → thoát với mã lỗi. Không có --check thì nó ghi đè file thật.

🧩 Pattern — "commit code sinh + kiểm tra độ tươi"

Có hai trường phái với code sinh tự động: (1) sinh lúc build (build script build.rs), không commit; (2) sinh một lần, commit kết quả, và có test đảm bảo nó khớp với nguồn. Dự án chọn (2): người dùng thư viện không phải chạy generator (không cần rustfmt, không tốn thời gian build), code sinh đọc được trên GitHub, rust-analyzer "go to definition" vào được. Cái giá: phải nhớ chạy lại generator — và bước kiểm tra này tồn tại để bạn không thể quên. (Ngoài bước này còn có test crates/openxml-codegen/tests/up_to_date.rs làm đúng việc tương tự trong cargo test.)

9.5 Bước 4 — toàn bộ test (dòng 20)

OPENXML_REQUIRE_XMLLINT="${…:-0}" cargo test --workspace. Cú pháp BIẾN=giá_trị lệnh đặt biến môi trường chỉ cho lệnh đó. Crate openxml-testkit đọc biến này: nếu máy không có xmllint thì mặc định (0) chỉ in ghi chú và bỏ qua phần kiểm tra XSD; đặt OPENXML_REQUIRE_XMLLINT=1 thì thiếu xmllint là lỗi. 11. Góc OpenXML: nguyên liệu của dự án và lệnh openxml info

Một thư viện OpenXML cần hai thứ "nguyên liệu" ngoài code:

  • schemas/ — các file XSD chính thức của ECMA-376 (Transitional, Strict, OPC) và dữ liệu trích từ PDF đặc tả. Đây là đầu vào của trình sinh code và của bước kiểm tra XSD.
  • fixtures/ — file Office thật để test: 45 file trong fixtures/poi/ (18 .docx, 14 .xlsx, 13 .pptx) lấy nguyên vẹn từ bộ test của dự án Java Apache POI (giấy phép Apache 2.0, xem fixtures/poi/NOTICE.md), và 1 file fixtures/ecma/PivotTableFormats.xlsx đi kèm bản phân phối ECMA-376. Theo fixtures/README.md, test crates/openxml-schema/tests/corpus.rs round-trip mọi part XML của mọi file ở đây.

Giờ đến phần thưởng. Ở bài 0.1 bạn giải nén sample.docx bằng tay; bây giờ dùng CLI của dự án:

Đối chiếu với bài 0.1:

  • Package: cả file sample.docx, được mở bằng Package::open_path.
  • main part: /word/document.xml: tìm ra bằng cách đi theo relationship officeDocument từ / (dòng / --officeDocument--> word/document.xml) — đúng như Word làm, không đoán theo tên.
  • Part name bắt đầu bằng /; cột bytes là kích thước dữ liệu của part (sau giải nén).
  • Content type: cột cuối, lấy từ [Content_Types].xml. Để ý [Content_Types].xml và các file .rels không xuất hiện trong danh sách part: theo OPC chúng không phải part mà là cấu trúc của chính package — thư viện đọc chúng vào bảng content type và danh sách relationship.
  • Relationship: Target in ra là tương đối so với part nguồn (styles.xml nghĩa là /word/styles.xml) — đúng "chỗ hay nhầm" ở bài 0.1.
  • creator: rỗng: core.xml của file này có thẻ dc:creator nhưng không có chữ nào bên trong.

Và đây là đoạn code in ra phần giữa output ở trên — đọc lướt thôi, bạn sẽ quay lại ở Phần 7:

  • say! là một macro tự viết của CLI (định nghĩa ở dòng 23–33), gần giống println!.
  • {:<48}: căn trái trong 48 ký tự; {:>9}: căn phải trong 9 ký tự — đó là lý do các cột thẳng hàng.
  • pkg.parts() trả về từng cặp (tên part, part) theo thứ tự tên — vì vậy danh sách part được sắp xếp. package_relationships() là quan hệ cấp gói (file _rels/.rels), còn part.relationships() là quan hệ của từng part (word/_rels/document.xml.rels…).
  • short_type cắt URI loại quan hệ dài (http://schemas.openxmlformats.org/officeDocument/2006/relationships/styles) lấy đoạn cuối (styles).
🦀 Góc Rust — vì sao binary tên là openxml?

Crate tên openxml-cli, nhưng file chạy là target/debug/openxml. Lý do nằm trong crates/openxml-cli/Cargo.toml: khối [[bin]] với name = "openxml" và path = "src/main.rs". Không có khối đó, cargo mặc định lấy tên package. Bạn có thể cài nó vào máy như một lệnh thật: cargo install --path crates/openxml-cli → sau đó gõ openxml info … ở bất kỳ đâu.

🛠 Bài tập

  1. Ba loại test. Chạy cargo test -p openxml-opc. Đếm số unit test, integration test, doc-test. Mở crates/openxml-opc/tests/real_packages.rs và tìm xem hai integration test tên gì. Rồi chạy riêng một trong hai bằng --test real_packages <tên>.
  2. Làm một test thất bại (rồi hoàn tác). Trong crates/openxml-xml/src/ns.rs, ở test strict_maps_to_transitional, tạm đổi Ns::W thành Ns::X. Chạy cargo test -p openxml-xml strict và đọc thông báo assertion `left == right` failed: left, right là gì? Sau đó hoàn tác bằng git checkout crates/openxml-xml/src/ns.rs.
  3. CLI trên Excel và PowerPoint. Chạy cargo run -p openxml-cli -- info fixtures/poi/sample.xlsx (và SampleShow.pptx). Main part là gì? Tìm part chứa shared strings và relationship dẫn tới nó. Thử thêm lệnh text và cat <file> /xl/workbook.xml.
  4. Example và thư mục out/. Chạy cargo run -p openxml-docx --example create_report -- out/report.docx (trên máy mình in ra wrote … (35 paragraphs, 1 tables, 2 sections, 1 comments)), rồi cargo run -p openxml-cli -- info out/report.docx. So sánh với sample.docx: có part nào mới? Kiểm tra git status — vì sao out/ không hiện ra?

Tự kiểm tra

1. Khác nhau giữa rustup, rustc và cargo?
rustc là trình biên dịch; cargo quản lý dự án (đọc Cargo.toml, tải dependency, gọi rustc, chạy test, sinh doc); rustup cài và chuyển đổi các bộ toolchain (rustc + cargo + rustfmt + clippy…).
2. edition = "2024" và rust-version = "1.88" khác nhau thế nào? Vì sao 1.88?
Edition là bộ quy tắc ngôn ngữ mà crate được viết theo (mỗi crate tự chọn, các edition dùng chung được). rust-version là phiên bản rustc tối thiểu để build được. 1.88 là bản ổn định hoá let chains (if let … && let …) cho edition 2024, thứ dự án dùng ở nhiều chỗ.
3. Trong cargo run -p openxml-cli -- info a.docx, dấu -- để làm gì?
Ngăn cách tham số của cargo với tham số của chương trình được chạy. info a.docx được chuyển nguyên cho binary openxml.
4. [profile.dev.package."*"] opt-level = 1 tối ưu cái gì, và vì sao đáng làm?
Tối ưu nhẹ mọi package không thuộc workspace (quick-xml, zip, flate2…) khi build dev/test. Test dành phần lớn thời gian giải nén ZIP và phân tích XML trong các dependency đó, nên chạy nhanh hơn; dependency chỉ biên dịch một lần nên chi phí gần như không có, còn code của dự án vẫn opt-level 0 để biên dịch lại nhanh.
5. Vì sao check.sh viết ${OPENXML_CORPUS:-} chứ không phải $OPENXML_CORPUS?
Vì script bật set -u: đọc một biến chưa gán là lỗi và script dừng. :- cho giá trị mặc định (ở đây chuỗi rỗng) khi biến chưa được đặt.
6. Bước "generated code is up to date" kiểm tra điều gì, và nếu nó báo lỗi thì làm gì?
Nó sinh lại code từ schemas/transitional/*.xsd (+ spec-index.json), định dạng bằng rustfmt với rustfmt.toml, rồi so từng file với crates/openxml-schema/src/generated/. Khác nhau → báo file "stale". Sửa bằng cách chạy cargo run -p openxml-codegen để ghi lại các file đó (và commit chúng).
